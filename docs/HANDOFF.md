# Handoff: StudioEncoder

For a new Claude Code session on another machine. Read this first, then `README.md`, `docs/phase0-design.md` and `docs/phase1-report.md`.

## What this is

A Windows OBS 33 plugin (StudioEncoder, folder and DLL `obs-studioencoder`) that adds ProRes-compatible video encoders for Standard recording, 4K 10-bit 4:2:2, from OBS's P216 output format:

1. **ProRes (FFmpeg prores_aw, fast)**: FFmpeg's `prores_aw` (the same code as FFmpeg's default `prores`). Recommended.
2. ~~ProRes (FFmpeg prores_ks)~~: removed in 0.14.0 (see "Settings window regroup and prores_ks removal" below).
3. **ProRes-compatible (Rust / FilmCraft)**: Rust encoder from the FilmCraft project (MIT OR Apache-2.0), pinned to commit `68919ed87aa6a097a4d21414ec7c438883f5fe22`. Heavy CPU use.

Unofficial; not Apple ProRes. Keep that wording in any user-facing text.

Current version: **0.16.0**.

## Layout

- `src/`: C glue. `encoder-common.c/.h` has the shared pipeline, P216 conversion and overload check. `encoder-ffmpeg.c` has the FFmpeg encoders: prores_aw (original), NVENC H.264 4:2:2, NVENC HEVC 4:2:0 and AMD HEVC 4:2:0 (see "AMD HEVC intra encoder" below). `encoder-qsv.c` has the Intel QuickSync HEVC 4:2:2 encoder (oneVPL, see "Intel QuickSync HEVC 4:2:2 intra encoder" below). Also `encoder-rust.c`, `prores-rs.h` and `plugin-main.c`. `capture-p210.cpp` is the 10-bit 4:2:2 capture source (Windows only).
- `tools/`: `prores-aw-test.c` (AW+ test program) and `p210-probe.cpp` (checks whether a capture card's P210 output carries real 10-bit data; build line at the top of the file).
- `rust/`: Rust C-ABI staticlib (`src/lib.rs`) wrapping the FilmCraft crate. Built by CMake through cargo.
- `harness/`: Rust benchmark CLI used in phase 1 (`prores-bench`).
- `scripts/install.ps1`: installs into a portable OBS (`-Portable <folder>`), or into the system OBS at `C:\ProgramData\obs-studio\plugins`. Removes legacy-layout copies.
- `scripts/package.ps1`: builds `obs-studioencoder-<version>-windows-x64.zip` for portable OBS.
- `scripts/test-record.ps1`, `scripts/test-cycles.ps1`: automated recordings in a portable OBS under `_test\obs-33.0.1`, which is not in git. Download the official 33.0.1 portable zip there first. These scripts overwrite that copy's test profile.
- `buildspec.json`, `CMakePresets.json`, `CMakeLists.txt`, `cmake/`: build setup from obs-plugintemplate, pinned to OBS 33.0.0 sources and obs-deps 2026-10-23.
- Not in git: `_ref/` (reference clones of obs-studio, obs-plugintemplate, filmcraft and StreamFX-Public), `.deps/`, `build_x64/`, `_test/`, `test-output/`, zips.

## Build (Windows)

Needs:
- Visual Studio 2026 Build Tools (C++ workload, Windows SDK 10.0.26100)
- CMake 3.28 or newer
- Rust stable `x86_64-pc-windows-msvc`

Then:

```
cmake --preset windows-x64
cmake --build build_x64 --config Release
powershell -ExecutionPolicy Bypass -File scripts\package.ps1
```

The first configure downloads OBS 33.0.0 sources and obs-deps into `.deps\` and builds libobs, which takes a few minutes. Cargo fetches FilmCraft at the pinned commit.

## Build and test on Linux (prepared 2026-11-03, built and tested on Linux 2026-11-03/04)

Status: built and tested on Linux. Results are in "Linux results" below. Short version: the AW+ ProRes encoder works on stock Ubuntu with no patching; the NVENC encoder and 10-bit capture need non-stock pieces (see below). The instructions below are the original plan; the only correction is that `libsimde-dev` was missing from the setup script (added, commit fa8fece). Original target: Mike's laptop (Core Ultra 9 185H, RTX 4070 Laptop) booted from a Linux USB SSD; also tested on the Ryzen 9 9950X3D / RTX 5080 desktop (same Linux install).

What was prepared:
- `CMakePresets.json` has the template's `ubuntu-x86_64` preset (Ninja, output in `build_x86_64/`). It uses the system's OBS, Qt 6 and FFmpeg development files; nothing is downloaded into `.deps` on Linux.
- `CMakeLists.txt`: `OBS::obs-frontend-api` may already come from `cmake/linux/defaults.cmake`; the Rust static library links `Threads`, `dl`, `m`, `rt`; `manifest.json` installs next to the data files and says `linux-x86_64`.
- C code: the MSVC-only parts already had GCC/Clang alternatives (`__builtin_cpu_supports("avx2")`, `__builtin_ctz`, `target("avx2")` functions). The NVENC encoder and its start-up check now treat an FFmpeg without the `high422` profile (older distro FFmpeg, roughly before 7.1) as "not available" instead of silently encoding 4:2:0.
- Scripts (bash): `scripts/linux-setup-ubuntu.sh` (apt packages incl. the official OBS PPA, rustup; uses sudo, so Mike runs it), `scripts/linux-build.sh`, `scripts/linux-install.sh` (to `~/.config/obs-studio/plugins/obs-studioencoder/bin/64bit/obs-studioencoder.so` + `data/`, no sudo; removes old `obs-prores` and `obs-studioencoders` folders), `scripts/linux-test.sh` (AVX2 DCT self-test, byte-identical checks against the system FFmpeg's prores_aw on all profiles at 4K and 1918x1082 for both AVX2 and plain C, AVX2 vs C at the shipped rounding, speed). `linux-test.sh` was dry-run in Git Bash on Windows with the Windows test program and passed every check.

Steps for the Linux session:
1. `git clone https://github.com/MolecularDust/StudioEncoder.git` (private; log in with `gh auth login` or a token), `cd StudioEncoder`, read this file.
2. `bash scripts/linux-setup-ubuntu.sh` (Mike runs it: sudo). Then a new terminal (for cargo).
3. If `/usr/include/obs/obs-module.h` is missing, the OBS package has no development files: build OBS 33.0.x from source (`obsproject/obs-studio`, tag 33.0.1, Linux build instructions in its wiki) and install it, or point CMake at it with `-DCMAKE_PREFIX_PATH`.
4. `bash scripts/linux-build.sh`. Expect first-build fixes: GCC warnings the Windows build never saw, header paths for obs-frontend-api, possibly the FFmpeg finder. Fix them in the repo (keep the Windows build working: it uses the same files).
5. `bash scripts/linux-test.sh` (optionally with a 4K clip path, e.g. a recording from the Windows drive). All checks must pass; any DIFFERENT means a real bug (or a distro FFmpeg whose prores_aw changed: compare its version first).
6. Close OBS, `bash scripts/linux-install.sh`, start OBS from a terminal (`obs`), check the log (Help > Log Files) for `[obs-studioencoder] loaded version`, `aw+: DCT uses AVX2`, and the NVENC line (on the RTX 4070 it should say not available). Tools > StudioEncoder should open the settings window.
7. Record 1 minute with SE: ProRes (AW+, fast) at Proxy and LT (Settings > Advanced: Color Format P216, Rec. 709, Limited; Output: Advanced, Recording Type Standard, MOV). Check the log's repeat summary, `ffprobe` the files (apco/apcs, yuv422p10le), and decode them with `ffmpeg -v error -i file -f null -`.

Linux notes:
- Use the native OBS package, not the Flatpak: a Flatpak plugin must be packaged as a Flatpak extension (separate work).
- Capture cards: V4L2 sources in OBS on Linux; which pixel formats each card offers there is untested. P216 output and the plugin do not depend on it.
- The NVENC encoder needs the NVIDIA driver plus an FFmpeg whose `h264_nvenc` lists `high422` and an RTX 50 card. That depends on the FFmpeg being built against nv-codec-headers 13.0 or newer, not on the FFmpeg version alone (the "7.1 or newer" wording here was wrong): Ubuntu's FFmpeg 8.0.1 hides it, CachyOS's FFmpeg 9.0.2 has it. Check with `ffmpeg -h encoder=h264_nvenc | grep high422`.
- Arch and derivatives: use `scripts/linux-setup-arch.sh` instead of the Ubuntu one (see "Linux results: CachyOS").
- Windows `scripts/*.ps1` do not apply on Linux; the Windows build is unchanged (preset `windows-x64`).

## Linux results (2026-11-03/04)

Environment: Ubuntu (apt suite "resolute"), kernel 7.0.0-42-generic, OBS 33.0.0 from the official PPA (native, not Flatpak), system FFmpeg 8.0.1-3ubuntu2, GCC 15.2, CMake 4.2.3, Rust 1.99.1 (rustup), NVIDIA driver 595.99.02 on the desktop.

**Build and tests (no patching needed)**
- `linux-build.sh` compiled cleanly on the first try once `libsimde-dev` was installed (libobs needs SIMDe headers to configure).
- `linux-test.sh`: ALL CHECKS PASSED. AVX2 DCT vs C: 4,000,000 blocks, 0 mismatches. Rounding off: byte-identical to the system FFmpeg prores_aw on all 4 profiles at 3840x2160 and 1918x1082, both AVX2 and plain C. Shipped rounding: AVX2 == C on all profiles. Single-thread 4K on the laptop under the `powersave` governor (slower than the Windows numbers): Proxy 42.4 ms AVX2 / 65.7 C, LT 70.9 / 101.2, 422 113.2 / 127.1, HQ 132.8 / 141.3.
- The plugin loads in OBS 33 (`loaded version 0.10.3`, `aw+: DCT uses AVX2`). Not checked: the Tools > StudioEncoder settings window.
- Recordings of a looped synthetic noisy 4K clip (laptop, P216, MOV): Proxy 1842 frames, 0 repeats, 39 ms per frame, 297 Mbit/s, OBS CPU 18%. LT 1891 frames, 14 repeats (0.7%, starting about 48 s in), 68 ms per frame, 624 Mbit/s, CPU 24%. Likely the powersave governor plus a very noisy clip; not re-tested with a performance governor. Both files: apco/apcs, yuv422p10le, bt709, decode clean.
- Desktop (RTX 5080), AW+ Proxy 4K 30: 1823 frames, 18.2 ms per frame, 0 repeats.
- Test tips: OBS 33 reads the active profile and scene collection from `user.ini` `[Basic]` (Profile, ProfileDir, SceneCollection, SceneCollectionFile). `obs --startrecording` works. SIGTERM/SIGINT do not stop OBS cleanly and leave an unfinalized MOV; stop through obs-websocket (`StopRecord`) instead. Delete `~/.config/obs-studio/.sentinel*` before a scripted start, or OBS waits at the safe-mode prompt. The test driver script was not added to the repo.

**NVENC H.264 10-bit 4:2:2 on Linux**
- Cause of "hidden / grayed out": Ubuntu's FFmpeg 8.0.1 `h264_nvenc` lists only baseline/main/high/high444p. FFmpeg's NVENC 4:2:2 support exists in the 8.0.1 source but is compiled in only when FFmpeg is built against nv-codec-headers 13.0 or newer. The old probe message "needs FFmpeg 7.1 or newer" was wrong and is corrected.
- Workaround used: FFmpeg 8.0.1 built with nv-codec-headers n13.0.19.0 into `~/nvenc-ffmpeg/prefix` (`--enable-shared --disable-x86asm --disable-doc --enable-nvenc`, no zlib so no PNG decoder, which only affects OBS interface images), and OBS started with `LD_LIBRARY_PATH` pointing at it (`obs-with-nvenc.sh`). A normal OBS start uses the system FFmpeg and the encoder is hidden again ("(Deprecated)" label on a profile that already uses it, or the "FFmpeg loaded by OBS is too old" error).
- Code change needed (also relevant to Windows if its FFmpeg is 8.0.1 or newer): with `gop_size = 1` FFmpeg 8.0.1's nvenc.c keeps the preset's B-frame interval and NVENC rejects it ("Gop Length should be greater than number of B frames + 1"). Intra-only needs `gop_size = 0` (gopLength 1, frameIntervalP 0). Changed in both the encoder setup and the probe in `src/encoder-ffmpeg.c`. Uncommitted at the time of writing.
- Results on the desktop: from 8-bit YUYV, 1828 frames, 15.6 ms per frame, 0 repeats, 200 Mbit/s. From P010 capture, 60 s: 1835 frames, all I, High 4:2:2 Intra yuv422p10le, 202.9 Mbit/s, 15.7 ms per frame, 0 repeats, 0 duplicated frames, full decode clean, about 611 distinct luma levels with 25% divisible by 4 (genuine 10-bit data).
- Not shippable as is: no distro FFmpeg has this. Realistic routes are calling NVIDIA's NVENC API directly (as OBS's own obs-nvenc does) or shipping a private FFmpeg; the plugin runs in OBS's process and shares OBS's libavcodec, so a private FFmpeg is awkward.

**Capture cards and 10-bit on Linux**
- AverMedia Live Gamer Ultra 2.1 (07ca:2553) is a UVC device with no vendor Linux driver. Its USB descriptor lists YUY2, NV12, MJPEG and P010 (GUID 30313050-...), but the stock `uvcvideo` drops P010, so only 8-bit formats appear. (07ca:d553 is the card's RGB-lighting HID controller, not a video device.) P010 is 4:2:0, so this card can never give 10-bit 4:2:2.
- Speed on the laptop (4K): YUYV 18 fps, NV12 24 fps, P010 12 fps (about 295 MB/s ceiling) even though the link is 10 Gbps; 1080p/1440p run at full rate; 4K MJPG runs at 60 fps. Raising the UVC transfer buffers (16 URBs x 512 packets) gained only about 5%. On the Ryzen desktop the same card delivers 4K YUYV, NV12 and P010 at a full 30 fps (P010 needs about 750 MB/s), so the limit was the laptop's USB path, not the card or the Linux driver.
- A first Linux recording from the card at 4K YUYV had 46% exact duplicate frames (the source delivered about 16 fps; OBS "Leave Unchanged" had picked 50 fps). The Windows recordings from the same card (e.g. `2026-11-03 13-09-45.mov`, `14-10-19.mov`, `14-11-38.mov`) have 0 duplicates, so the Windows driver sustains 4K 30 on that laptop and the Linux driver does not.
- OBS 33's Linux sources cannot take P010: `plugins/linux-v4l2` (`v4l2_to_obs_video_format`) maps only YVYU, YUYV, UYVY, NV12, I420/YV12, BGRX/BGRA and BGR24 and hides every other format; `linux-pipewire` has only 8-bit formats plus two 10-bit RGB ones. OBS core itself supports P010 sources (GS_R16 plane plus GS_RG16 chroma plane).
- Magewell Pro Capture HDMI 4K on Linux (Magewell driver 1.3.0.4458, V4L2): only 8-bit formats (YUYV, UYVY, NV12, YV12, YU12, RGB3, RGB4, BGR3, BGR4, GREY, Y16, YUV4). No 10-bit colour format through V4L2.
- DeckLink: OBS 30 added 10-bit DeckLink capture; not tested here. The Flatpak OBS cannot use Blackmagic hardware.
- Experiment that got P010 into OBS (not in the repo; sources live under the home folder on the Linux install: `~/uvc-p010`, `~/obs-v4l2-10bit`, `~/nvenc-ffmpeg`):
  1. Kernel: add a P010 entry (GUID `30313050-0000-0010-8000-00aa00389b71`, fcc `V4L2_PIX_FMT_P010`) to `uvc_fmts[]` in `drivers/media/common/uvc.c` (v7.0; in this kernel the table lives in the separate `uvc` module). Built out of tree and loaded with `rmmod uvcvideo uvc; insmod uvc.ko; modprobe uvcvideo`. Lost at reboot.
  2. OBS: a copy of `plugins/linux-v4l2` (33.0.0) built as a separate module `obs-v4l2-10bit` with source id `v4l2_input_p010` ("Video Capture Device (V4L2, 10-bit P010)"): P010 added to the format map and the two-plane layout. `uvcvideo` reports `bytesperline` as width x 3 for P010 (from the descriptor's 24 bits per pixel); the real stride is width x 2, and using the reported value gave a doubled, striped, green/magenta picture and froze OBS (chroma plane read past the buffer end). The source overrides the stride. Also added a "Deactivate when not showing" option: the stock Linux V4L2 source holds the device while it exists, so two sources on one card cannot both run. A plugin needs a `data/manifest.json` or OBS 33's Plugin Manager leaves its sources disabled.
- Result: P010 4K 30 from the AverMedia on the Ryzen desktop into the NVENC encoder, clean, as above.

**Assessment (for product decisions)**
- AW+ (software ProRes) is close to shippable on Linux with no kernel, FFmpeg or driver changes. Remaining work is packaging (.deb/PPA; Flatpak needs a Flatpak extension, untested), longer soaks and start/stop cycles on Linux, other distros and OBS versions, and CI.
- NVENC 4:2:2 and true 10-bit capture on Linux depend on things outside the plugin (distro FFmpeg build flags, kernel UVC format table, OBS camera sources, vendor drivers). Do not promise them. Recordings are 10-bit 4:2:2 files either way; with an 8-bit source the content is 8-bit detail in a 10-bit file, same as on Windows.
- A user-facing manual page for Linux was drafted (`StudioEncoder-on-Linux.md` / `.html`, kept outside the repo at the time of writing).

**Magewell Pro Capture HDMI 4K (PCI 1cd7:0012) on CachyOS**
- Driver `ProCaptureForLinux_1.3.4458` (module 1.3.0.4458). The kernel is a Clang/ThinLTO build, so the module builds only with `make LLVM=1`; Magewell's `install.sh` uses plain `make` (GCC) and its `dkms-install.sh` registers the name `ProCapture` while `src/dkms.conf` says `ProCaptureForLinux`, so neither was used. A DKMS install with a corrected `dkms.conf` worked and rebuilds on kernel updates: `PACKAGE_NAME=ProCapture`, `PACKAGE_VERSION=1.3.4458`, `MAKE[0]="make LLVM=1 KERNELDIR=/lib/modules/${kernelver}/build"`, source copied to `/usr/src/ProCapture-1.3.4458`, plus `ProCapture.conf` (modprobe), the udev rule and `mwcap-info` / `mwcap-control` from the package. Secure Boot was off. Only the main kernel was covered (the LTS kernel has no headers installed).
- V4L2 formats: YUYV, UYVY, NV12, YV12, YU12, RGB3/4, BGR3/4, GREY, Y16, YUV4. No 10-bit.
- **The card sits in a PCIe x1 slot** (negotiated Gen 2, 5 GT/s, x1; the card can do x4). 4K30 YUYV needs about 497 MB/s, more than a Gen 2 x1 link delivers (about 400 MB/s usable). OBS counted 6400 captured frames in 256 s, about 25.0 fps, and the files show 16.7% identical consecutive frames (1 in 6), while the plugin counted 0 repeats. The earlier Windows note blaming a 25p camera for the same 17-18% on the desktop may be this slot limit instead; check. This board has no x4 slot; a new motherboard is on order. **Re-test the Magewell with 4K30 YUYV after the swap** (expect 0% identical frames; check `current_link_width` is 4).
- The 8.0% in the NVENC take is not explained by a flat 25 fps cap; not investigated.

**Shipping notes (from the CachyOS test)**
- The plugin binary links the distro's FFmpeg soname (here `libavcodec.so.63`, `libavutil.so.61`; Ubuntu's FFmpeg 8 is `.62` / `.60`), so a binary built on one distro will not load on another. Options: per-distro builds, or stop linking libavcodec for the parts that do not need it (AW+ is a standalone port).
- The NVENC encoder depends on how the distro compiled FFmpeg. The robust route is NVIDIA's NVENC API directly, loaded at run time, as OBS's own `obs-nvenc` does.
- Also open: Flatpak extension, other distros (Fedora-based and Flatpak OBS), 10-bit capture needs an OBS V4L2 patch or a DeckLink-class source. The licence question (libobs is GPL; AW+ derives from FFmpeg's LGPL code) needs a proper look before any closed-source release.

## Linux results: CachyOS, 10-bit 4:2:0 and AMD (2026-11-07)

Scope agreed with Mike: Linux is for **10-bit 4:2:0** (P010) recording, with the AMD and NVIDIA HEVC encoders in the settings window's "10-bit 4:2:0" group (they are flagged `yuv420` in `src/settings.c`, so they sit there and not under "Recommended"). 10-bit 4:2:2 on Linux stays with AW+ (software) and the RTX 50 NVENC H.264 encoder; true 4:2:2 capture is out of scope on Linux (the DeckLink is the expected route later, untested).

**Hardware now:** the Ryzen desktop has a new motherboard (ASRock B650 Steel Legend WiFi) and a Radeon RX 9070 XT (Navi 48) in place of the RTX 5080; the NVIDIA driver finds no card, so both NVENC encoders are correctly hidden (`cuda_init_100`). Plugin 0.15.0 (pulled and rebuilt from `c996c94`; the installed folder is now `obs-studioencoder`, singular). The Magewell now negotiates PCIe Gen 2 **x4** (it was x1); a capture re-test with it is still open.

**AMD GPUs cannot encode 10-bit 4:2:2** (RX 9070 XT and the Ryzen's Radeon 610M, Mesa 26.2.6):
- `vainfo` lists no 4:2:2 profile and no H.264 High 10 on either GPU, only HEVC Main 10 (4:2:0), H.264 8-bit and AV1.
- `hevc_vaapi` and `h264_vaapi` with `yuv422p10le` input fail on both (`-22` / `No usable encoding profile found`), on synthetic frames and on live AverMedia frames. The same pipeline with `p010le` and `-profile:v main10` encodes fine.
- `hevc_amf` does not start on Linux here (`libamfrt64.so.1` not installed; not pursued).

**10-bit 4:2:0 capture works on CachyOS with a small OBS source patch**
- Kernel 7.3.1 lists P010 on the AverMedia card (07ca:2553) with no patching and reports `bytesperline` 7680 (width x 2), so the stride workaround from the Ubuntu experiment is no longer needed. The Ubuntu session found an upstream UVC commit for P010 (March 2026); which release first has it was not checked.
- ffmpeg tests with real frames, 10 s, 3840x2160 30 fps, HEVC Main 10 intra (`hevc_vaapi`, QP 18): YUYV capture on the RX 9070 XT (298 frames) and native P010 on the RX 9070 XT and on the 610M iGPU (300 frames each; ffmpeg's V4L2 input cannot take P010, so the frames came from `v4l2-ctl --stream-mmap` piped in as `-pix_fmt p010le`). All three: 3840x2160 verified with `ffprobe`, `yuv420p10le`, 0 identical consecutive frames, clean decode, a P010 frame looked at (correct colours, no striping). A first attempt that reported 4K but wrote 2560x1440 was a mistake in the test (ffmpeg took the card's previous mode); check the output size every time.
- **The OBS patch** (sources on the Ubuntu drive under `~/obs-v4l2-10bit`, written against OBS 33.0.0; the differences listed below were taken against the official 33.0.1 source): a copy of `plugins/linux-v4l2` built as its own module `obs-v4l2-10bit` with source id `v4l2_input_p010` ("Video Capture Device (V4L2)" in the list). ## Decisions made

- FFmpeg: option (a), build against the FFmpeg that obs-deps ships (avcodec 62, FFmpeg 8.x). Keep the backend seam so a bundled LGPL FFmpeg could replace it.
- Target OBS 33.0.0 / 33.0.1. No promise of OBS 32 compatibility.
- Input format P216. OBS 33 has no P210 or I210 output. Conversion is (v + 32) >> 6 per sample with SSE2.
- The muxer gets the FourCC through the encoder setting `codec_type`, as a big-endian integer. The encoder must return true from `get_extra_data`, or obs-ffmpeg-mux silently drops every packet.
- Frame-parallel pipeline: several frames encoded at once, each on its own worker and encoder context, returned in order.
- Automatic frames in flight is the default. It starts at half the logical CPUs and grows while the oldest frame is late, up to one worker per logical CPU. 0.4.1 also stopped growing once a worker "didn't help", which left prores_ks short on the 32-thread desktop; that rule was removed in 0.4.2.
- Stopping costs no frames. OBS keeps feeding the encoder until a packet past the stop point arrives.
- Overload detection (0.5.0): the plugin counts repeated frames itself, per recording. When encoding holds up OBS's video thread, OBS hands the encoder the same cached frame buffer again, so a repeat is "the same frame buffer twice in a row". It warns every overloaded second (more than 2% repeats), writes a summary at the end, and can optionally stop the recording after 3 overloaded seconds in a row. Earlier versions read OBS's shared `video_output_get_skipped_frames` counter. OBS resets that counter whenever an output connects, which made the summary wrong for later recordings in a session (0.4.1 and 0.4.2).
- Automatic sizing toggle (0.5.0): "Grow when frames are late" (default), or "Size from measured frame cost" (experimental). The second starts at 4 workers and jumps to ceil(fps x seconds per frame x 1.25) + 1, re-evaluated at most once a second, and only ever grows.
- NVENC H.264 10-bit 4:2:2 all-intra encoder (0.6.0), RTX 50 series only: FFmpeg `h264_nvenc` from OBS's obs-deps, P216 straight in (no conversion), profile high422, `-g 1 -bf 0`, CBR, `tune ll` (`tune hq` is rejected with a GOP of 1 at p4-p7), preset p5 or p1, `delay 0`, SPS/PPS in extradata (global header). Default 200 Mbit/s, chosen from the desktop FFmpeg test (`REPORT-INTRA.md`: 100M 58.8 dB, 200M 62.2 dB, 300M 65.3 dB; ProRes LT 59.7 dB). Max 2 frames in flight (NVENC session limit). The ProRes profile list, Threads setting and FourCC are hidden/zero for this backend. Pre-RTX-50 support (HEVC/AV1 4:2:0) is deferred. Tested in OBS on the desktop RTX 5080 with the AverMedia card (REPORT-NVENC-PLUGIN.md, 2026-11-03): 100/200/300 (p1) 1 min, 200 for 10 min and 5 start/stop cycles, all High 4:2:2 Intra yuv422p10le, every frame I, bitrate on target, 0 repeated frames (log and hashes), about 20 ms per frame, OBS about 1% CPU, NVENC about 27%. On the laptop RTX 4070 it fails cleanly with the RTX 50 message.
- Plugin Manager version (0.7.1): the OBS 33 Plugin Manager reads the version from `data/manifest.json`; `cmake/manifest.json.in` is filled from buildspec.json at configure time and installed by CMakeLists.txt. Verified: Tools > Plugin Manager > Installed shows "ProRes-compatible encoders 0.7.1".
- Settings window (0.8.0): Tools > "StudioEncoder" (Qt dialog, `src/settings-dialog.cpp`) lists all five encoders; Recommended (prores_aw, NVENC H.264) on, Experimental (prores_ks, FilmCraft, OxideAV) off by default. Choices live in `plugin_config\obs-studioencoder\settings.json` (written by the dialog, not meant to be hand-edited). A disabled encoder is registered with `OBS_ENCODER_CAP_DEPRECATED`, so OBS hides it from the dropdown (and its start-up encoder log) but profiles that already use it still work; OBS labels such a selected encoder "(Deprecated)". Toggles need an OBS restart because encoders register at load. Build: Qt6 (obs-deps qt6 2026-10-23, hash in buildspec.json, ~260 MB download into .deps) and obs-frontend-api; no Q_OBJECT classes, so no moc. Tested in the test OBS: menu item present, dialog defaults right, OK saves, restart lists OxideAV, a hidden encoder still records.
- Rename to StudioEncoder (0.9.0): chosen to keep "ProRes" out of the product name (Apple's trademark guidelines bar using its marks in product names; "ProRes" now appears only in descriptions). Module/folder/DLL/log prefix are `obs-studioencoder`; Plugin Manager and Tools menu say "StudioEncoder". Encoder IDs (`obs_prores_*`) are unchanged on purpose, so existing OBS profiles keep working. The Rust crate and CMake target are `studioencoder-rs` / `studioencoder_rs_build`. Settings now live in `plugin_config\obs-studioencoder\settings.json` (files saved under the earlier plugin folder names `obs-prores` and `obs-studioencoders` are not migrated; the settings are only the Recommended/Experimental encoder choices). `scripts/install.ps1` and `scripts/linux-install.sh` delete old `obs-prores` and `obs-studioencoders` plugin folders; anyone updating by hand must delete them too. The GitHub repo and the project folder are named StudioEncoder (renamed 2026-11-05, with the plugin id changing from the plural form to `obs-studioencoder`; encoder IDs and the saved profile references stayed the same).
- Hardware check and SE prefix (0.9.1): at start-up `pr_nvenc_h264_422_probe()` (encoder-ffmpeg.c) opens `h264_nvenc` in the same 10-bit 4:2:2 mode on a 256x256 frame and closes it (about 90 ms on the laptop). If it fails, the NVENC encoder is hidden from OBS's list (same DEPRECATED-cap mechanism) and shown grayed out in the StudioEncoder window; the saved choice is left untouched, there is no manual override, and the check runs again on every start. The log line says `hardware check passed` or `not available on this system, hidden` with the driver's reason. Laptop (RTX 4070): hidden, as expected. Verified on both machines (2026-11-03): offered on the desktop (RTX 5080), hidden and grayed out on the laptop (RTX 4070). All encoder names in OBS start with `SE: `.
- AW+ (0.10.0): `src/prores-aw.c` is a standalone port of FFmpeg 8.0's prores_aw (proresenc_anatoliy.c, jfdctint 10-bit, proresdata tables), progressive 4:2:2 only. The Proxy blur came from `level = coef / step` truncating toward zero (matrix and quantiser are identical to Apple's: both use q8 on 100% of slices). AW+ rounds with a per-profile offset (`pa_default_round8`: Proxy 4, LT 3, 422 3, HQ 2, eighths of a step; best quality per bit; full rounding at HQ made the rate control raise the quantiser). round8=0 is byte-identical to FFmpeg on all four profiles (`tools/prores-aw-test.c`, build target `prores-aw-test`). Speed: exact reciprocal multiply instead of division and a 32-bit bit writer; single-thread 4K Proxy 41 ms vs FFmpeg 52, HQ 79 vs 81. AW+ took over the ID `obs_prores_ffmpeg_aw` so existing profiles get it; FFmpeg's original moved to `obs_prores_ffmpeg_aw_original` (experimental). Test OBS, 4K: AW+ Proxy 11.4% CPU 94 Mbit/s, original 12.5% 74 Mbit/s; AW+ LT 13.0% 197 Mbit/s; no repeats. Visual check (eye crop) matches Apple Proxy.
- AW+ live test (2026-11-03, laptop, AverMedia + ZV-E1, YUY2, 4K 30, Proxy, 1 min each): AW+ 103 Mbit/s (0.78 GB), 41 ms per frame, OBS CPU 7%; original prores_aw 68 Mbit/s (0.51 GB), 48 ms, CPU 8%. No repeated frames in either; both `apco`, Rec. 709, decode clean. FFmpeg blurdetect over 60 frames: AW+ 8.0, original 9.7 (lower is sharper); a hair close-up shows individual hairs with AW+ and a smear with the original.
- 0.10.1 fixes: the per-frame packet buffer was width x height + 64 KB (8 MB at 4K); pure noise reaches 8.8 MB (Proxy) to 20 MB (HQ) per 4K frame, so very noisy footage could fail the encode. Now 3 bytes per pixel + 1 MB (about 26 MB at 4K, physical memory only for what is written). Verified: a looped 4K noise clip at HQ with AW+ recorded 500 frames of 10-15 MB, decode clean. The overload warning no longer names prores_aw ("Use a lighter profile or a lower resolution; SE: ProRes (AW+, fast) is the lightest ProRes encoder"). Code review findings that did not lead to changes: precise float DCT gains at most 0.15 dB for half the speed; low/high-frequency rounding splits were all worse than uniform rounding; Apple's quantisation matrices equal AW's in all profiles; rate control re-encodes 1.00-1.06 times per slice. Time split per 4K Proxy frame: DCT about 20 ms, quantise + entropy coding about 25 ms (HQ: 55 ms).
- AVX2 DCT (0.10.2): `fdct_get_avx2` in prores-aw.c runs fdct_10's integer algorithm on 8 lines at once (32-bit lanes, mullo/srai, 16-bit truncation where fdct_10 stores int16), chosen at the first pa_create when the CPU has AVX2 (cpuid + xgetbv), plain C otherwise; the log says `aw+: DCT uses AVX2`. Verified: `prores-aw-test selftest 4000000` = 0 mismatching blocks (random, all-0/1023, checkerboards); whole files with AVX2 still byte-identical to FFmpeg at round8 0 (4 profiles at 4K, 1920x1080, 1918x1082) and identical to the C path at the shipped rounding (incl. 4K noise at HQ); `PA_NO_SIMD=1` forces C in the test tool. Speed, single thread 4K: Proxy 40 -> 31 ms, LT 47 -> 39, 422 63 -> 55, HQ 74 -> 67. In the test OBS (11 frames in flight): Proxy 38.6 -> 33.8 ms per frame, CPU 11.7% -> 11.0%; LT 47.1 -> 42.7 ms, 12.6% -> 12.1%. Smaller than the 35% estimated: the AVX2 DCT still costs about half the C one (transposes, slow 32-bit multiplies). The next lever would be entropy coding, now the larger share (about 25 ms of a Proxy frame).
- Entropy coding (0.10.3): each codeword is now computed as one value + length (`vlc_code`) and the run code, level code and sign bit go out in one 64-bit write (`emit_ac`, `bw_put64`) instead of 3-5 bit-writer calls. With AVX2, `encode_acs_avx2` first tests every block 16 coefficients at a time (same |x| + offset >= q test, in 16 bits) to build a per-frequency bitmask of non-zero blocks, then jumps from one non-zero coefficient to the next (Proxy is almost all zeros, which the old loop tested one by one). Plain-C CPUs use `encode_acs_c`. Verified byte-identical, on both paths: FFmpeg match with rounding off (4 profiles), 0.10.2 output at shipped rounding (4 profiles), 4K noise at HQ and Proxy, 1918x1082 LT. Single thread 4K, AVX2 (plain C): Proxy 20.5 ms (37), LT 27 (43), 422 35 (54), HQ 42.5 (63); 0.10.1 was 40 / 47 / 63 / 74. Test OBS: Proxy 20.3 ms per frame, CPU 9.2% (0.10.1: 38.6 ms, 11.7%; scene alone about 5%); LT 27.1 ms, 9.9%; HQ 49.7 ms, 13.3%.
- 0.10.3 live test (2026-11-03, laptop, AverMedia + ZV-E1, YUY2, 4K 30, 1 min each): AW+ Proxy 20.1 ms per frame, OBS CPU 4.5% (0.10.0: 41 ms, 7%), 99 Mbit/s (0.75 GB/min); AW+ LT 31.3 ms, CPU 6%, 264 Mbit/s (2.05 GB/min). Log shows `aw+: DCT uses AVX2`; no repeated frames in either; both 10-bit 4:2:2, Rec. 709, decode clean.
- OxideAV ProRes encoder (0.7.0): `oxideav-prores` 0.1.1 + `oxideav-core` 0.1.42 (both MIT, pinned with `=` in rust/Cargo.toml), wrapped in `rust/src/lib.rs` (`ox_create/ox_encode/ox_destroy`) and `src/encoder-oxideav.c`, id `obs_prores_oxideav`. Uses `make_encoder_with_config` so the frame header carries colour tags and frame-rate code (the simple `encode_frame_*` functions leave them blank). Fixed quantiser per profile (no rate control), one frame per thread, so it relies on the frame-parallel pipeline: laptop 4K422 about 69 fps at 22 frames at once, 328 Mbit/s, 65.6 dB (benchmark in BENCHMARK-APV-OXIDEAV.md). Tested in the test OBS: all four profiles give the right FourCC, Rec. 709 tags, decode clean. Live test on the laptop with the AverMedia card (1 min each, 422): OxideAV 519 Mbit/s, 199 ms per frame, OBS CPU 30%; prores_aw 387 Mbit/s, 74 ms per frame, CPU 12%; no repeated frames in either. Quality per bit equal when re-encoding the same camera frames, so OxideAV has no advantage; prores_aw stays the recommended encoder.
- CPU comparison of the ProRes encoders (2026-11-03, laptop, test OBS, looped 4K clip, profile 422, 30 s window, share of 22 threads; scene alone costs 5.2%): prores_aw 15.2% (65 ms per frame, 1 repeat at start), OxideAV 31.2% (178 ms, no repeats), FilmCraft 66.0% (502 ms, 21.6% of frames repeated, overloaded). Encoder-only share: about 10%, 26% and 61%. Measured with `scripts/test-record.ps1` (prints "OBS CPU"; `-NoRecord` measures the scene alone).
- OxideAV live on the desktop (2026-11-03, plugin 0.7.1, Magewell + GH5S, 4K 29.97, profile 422, 1 min): 591 Mbit/s (4.5 GB), 161.5 ms per frame with 16 frames in flight (up to 32), OBS CPU 16% of 32 threads, no repeated frames; ProRes 422 (`apcn`), Rec. 709 tags, decodes clean. For comparison on the desktop: prores_aw about 8% and FilmCraft about 22% (earlier versions, different scene), so OxideAV is about 2x prores_aw there (2.6x on the laptop).
- 10-bit 4:2:2 capture source (0.11.0, Windows): the Magewell driver (1.3.0.4323) offers P210 through DirectShow, but OBS's Video Capture Device source cannot use it: libdshowcapture (OBS 33 and current master) maps formats only up to P010. `src/capture-p210.cpp` registers `studioencoder_p210_capture` ("SE: 10-bit 4:2:2 capture (P210)"): it opens the device in P210 at the chosen size and rate with a Sample Grabber + Null Renderer graph (qedit.dll, interfaces declared in the file), on its own MTA worker thread, and outputs async frames. OBS 33 accepts P216 source frames but has no conversion shader for them (`get_convert_type` returns CONVERT_NONE: nothing is drawn, recordings freeze), so each frame is converted to I210 (shift right 6, split CbCr; SSE2), 2.4 ms per 4K frame on the 9950X3D. With Color Format P216 OBS's canvas is RGBA16F, so the 10 bits reach the encoder. `tools/p210-probe.cpp` verified the card's P210 is real 10-bit with camera footage (612 distinct luma codes, lowest 2 bits non-zero in 76% of samples, no bit replication). Live test (2026-11-05, desktop, Magewell + camera, 3840x2160 29.97, AW+ 422, 20 s): 606 frames, no repeats in the log or by frame hash, `yuv422p10le`, decodes clean, picture correct. Not checked yet: whether the camera's HDMI signal itself is 10-bit (check the camera menu or the Magewell property page), audio (use a separate Audio Input Capture source), long runs and hot-plugging.
- Linux later: keep the code portable where practical (pthreads, libobs threading). Install paths differ.

## AMD HEVC intra encoder (0.12.0, 2026-11-06)

`SE: HEVC 10-bit Intra (AMD)` (`obs_prores_amd_hevc_intra`): FFmpeg `hevc_amf`, P010 in, 10-bit 4:2:0, gop_size 1 (every frame an IDR), constant quantiser, `profile=main10`. Built because AMD's VCN cannot do 4:2:2 (checked: OBS's own AMD H.264 refuses 10-bit with "Cannot perform 10-bit encode on AMD H.264 encoder"; HEVC and AV1 do 10-bit 4:2:0 only). The reason to have it is convenience: one Quality choice instead of OBS's AMF settings.

- **Presets** (QP 22 / 14 / 10 / 6 = Small / Standard / High / Maximum, default High): measured on the 4K 29.97 camera clip on an RX 9070 XT, 32 / 72 / 120 / 172 Mbit/s through the plugin. QP 6 is already the ceiling (CBR 200 and 300 gave the same 170 Mbit/s). AMF's CBR was not used: it misses its target badly in intra mode (50M asked, 67M made).
- **One frame of latency**: AMF returns the packet for a frame only after the next frame went in (checked with `-debug_ts` for every `usage` mode). The backend therefore runs one context (`max_in_flight 1`, about 3.8 ms per 4K frame, plenty) and keeps OBS's timestamps in a small queue. `encoder-common.c` accepts `out_size 0` from `encode()` as "no packet yet", and `pr_planes` carries `pts` / `out_pts`. The last frame before Stop is lost (OBS does not flush video encoders).
- **Probe size**: AMF refuses 256x256 (`Init() failed with error 5`); the start-up check uses 640x360.
- **Without `profile=main10`** the plugin's stream said Main (idc 1) while holding 10-bit data; the FFmpeg command line said Main 10 for the same options. Cause not found, explicit setting fixes it.
- `encoder-common.c` now takes the input format from the backend (`input_p010`), copies a half-height CbCr plane for P010, and has per-backend log text and Info text. The NVENC path (P216) was changed only in how the plane copy loop is written; it could not be run on this machine (no NVIDIA card now), so re-test NVENC on the laptop or an RTX 50 card before release.
- Tested on the desktop in a stock portable OBS: 212 frames recorded, all keyframes, pts steps of exactly 1001, clean FFmpeg decode, no repeated frames; wrong Color Format gives a clear error; ProRes AW+ unaffected. **Not tested**: Resolve and Premiere playback, 4K60, 8K, long recordings, AMD cards other than the RX 9070 XT, AV1 (an intra AV1 variant is possible later).

## NVIDIA HEVC intra encoder (0.13.0, 2026-11-07)

`SE: HEVC 10-bit 4:2:0 Intra (NVIDIA NVENC)` (`obs_prores_nvenc_hevc_intra`): FFmpeg `hevc_nvenc`, P010 in (like the AMD encoder: `input_p010`, the shared code copies the half-height CbCr plane), `profile=main10`, `gop_size 0` (NVENC's explicit intra-only mode, as in the H.264 backend), CBR with the same `bitrate_mbps` / `nvenc_preset` settings as the H.264 NVENC encoder, `tune ll`, `delay 0`, max 2 frames in flight. For GeForce cards without the RTX 50 H.264 4:2:2 mode. Start-up probe `pr_nvenc_hevc_probe` opens it at 640x360 (about 96 ms).

- Measured on the RTX 4070 Laptop (luma PSNR vs the 4:2:2 camera clip, 20 frames): 40 / 60 / 80 / 100 / 150 / 200 / 300 Mbit/s targets gave 39 / 58 / 77 / 98 / 145 / 203 / 274 Mbit/s at 53.6 / 55.3 / 56.5 / 57.6 / 59.4 / 60.8 / 63.0 dB; AW+ for scale: Proxy 95 Mbit/s 53.7 dB, LT 200 Mbit/s 59.6 dB, HQ 564 Mbit/s 72.2 dB. - Test OBS (looped 4K clip, 25 s each): 100 / 150 / 150 p1 / 250 Mbit/s gave 100.1 / 150.0 / 149.9 / 254.6 Mbit/s, every frame I, `Main 10`, `yuv420p10le`, 0 decode errors; 15.2 ms per frame; OBS CPU 6.7-7.1% (scene alone about 5%); one repeated frame at start-up in some takes, as with the other encoders.
- **`hvc1` tag**: the muxer's default for HEVC in MOV is `hev1`, which Apple's players and some editors do not read. New backend field `container_tag` (FOURCC macro now in encoder-common.h) is published as `codec_type`, which the OBS muxer passes through as the sample-entry tag. Set only for this encoder. The AMD encoder (0.12.0) still writes `hev1`: not changed because it cannot be tested on this laptop; the same one-line `.container_tag` fix would apply.
- Not tested: Resolve and Premiere playback, GTX 10/16/RTX 20/30 cards (only the RTX 4070 Laptop), RTX 50 for this encoder, 4K60, long recordings. The settings window was checked: on the laptop the new encoder is ticked and available, the RTX 50 H.264 and the AMD encoder are grayed out.
- The NVENC H.264 4:2:2 re-test noted for 0.12.0 is still open (needs an RTX 50 card). This encoder exercises the same P010 copy loop on NVENC and it is clean, which makes a regression in the shared plane copy less likely but does not cover P216.

## Settings window regroup and prores_ks removal (0.14.0, 2026-11-07)

- **Window**: three sections. ## Intel QuickSync HEVC 4:2:2 intra encoder (0.16.0, 2026-11-09)

Machine: a third laptop, Intel Core Ultra X7 358H with Arc B390 graphics (no NVIDIA, no AMD), Windows 11, Intel graphics driver as shipped. Capture: the AverMedia Live Gamer Ultra 2.1 in P010 4K 30 (DirectShow), with the camera on it.

**Why:** OBS's own QuickSync HEVC refuses Color Format P216 ("Cannot perform 16-bit encode on this encoder"), so stock OBS cannot record 10-bit 4:2:2 on Intel. The hardware can: FFmpeg's `hevc_qsv` (Gyan build 9.0.2) encodes 4K 10-bit 4:2:2 intra (`-profile:v rext`, input `y210`) at about 65 fps on a test pattern, and a 30 s live take from the card (P010 piped in by a small DirectShow tool, converted to Y210) gave 901/901 frames, 0 dropped, 0 repeats, 1.0x real time, 120 Mbit/s at ICQ 18. For comparison, OBS's own QuickSync HEVC with Color Format P010 held 30 fps (868 frames in 28.9 s, 0 repeats).

**`SE: HEVC 10-bit 4:2:2 Intra (Intel QuickSync)`** (`obs_prores_qsv_hevc422_intra`, `src/encoder-qsv.c`):
- **oneVPL directly, not FFmpeg**: OBS 33's bundled FFmpeg (obs-deps 2026-10-23, `avcodec-62.dll`) has no QuickSync encoders at all (`hevc_qsv` and `h264_qsv` missing; `hevc_amf` and `hevc_nvenc` present). obs-deps does ship the oneVPL headers (`include/vpl`) and the static dispatcher `lib/vpl.lib`, without a CMake package; `CMakeLists.txt` finds them itself and builds the encoder only when found (`SE_HAVE_VPL`), so builds without oneVPL still work.
- P216 in (Color Format P216), repacked on the worker thread to Y210 (Y0 Cb Y1 Cr, 10 bits at the top of each 16-bit word, rounded with (v + 32) & 0xFFC0, SSE2), system-memory surfaces, HEVC Main 4:2:2 10 (Rext), GOP 1 with every frame forced IDR, ICQ rate control, `hvc1` tag, VPS/SPS/PPS read with `GetVideoParam` for the MOV header, Rec. 709 colour tags through `mfxExtVideoSignalInfo`.
- **Pipelining matters**: sending a frame and waiting for it before the next (AsyncDepth 1) took 36.6 ms per 4K frame and OBS repeated 69% of frames. Now 3 frames are queued in the hardware and each packet is collected 2 frames later (timestamps come back through `mfxBitstream.TimeStamp`): 2.5-2.9 ms per frame on the worker, about 6-7 ms on OBS's thread. One encoder session (`max_in_flight 1`). The last frames before Stop may be lost (OBS does not flush video encoders), as with the AMD encoder.
- Quality presets (ICQ 24 / 21 / 18 / 12 = Small / Standard / High / Maximum, default High). Through FFmpeg on the live clip: 32 / 89 / 120 / 160 Mbit/s. Through the plugin on a different live scene, High gave 170 Mbit/s, so the preset labels are rough; re-measure on one clip before relying on them. CQP through FFmpeg's `-q:v` / `+qscale` did not change the bitrate at all (always about 174 Mbit/s), ICQ did.
- Start-up probe opens the encoder at 640x360 and closes it (about 450 ms on this laptop, slower than the other probes).
- **Tested** in a stock portable OBS 33.0.1 (`_test`), plugin 0.16.0: synthetic 4K 29.97, 398 frames, 0 repeats, 2.5 ms per frame. Live AverMedia P010 4K 30 into P216, 60 s: 1901 frames, OBS CPU 4.2% of 16 threads, plugin counter 1 repeat (first second), file 1896 frames, HEVC Rext `yuv422p10le` `hvc1`, Rec. 709 limited, every frame a keyframe, 170 Mbit/s, gapless timestamps, clean full decode, picture checked. Frame hashes show 29 identical frames, all in the first second (frames 1-29: the card still starting while OBS was already recording), none in the remaining 1866. AW+ Proxy re-tested after the change (apco, clean decode, no repeats).
- **In Mike's own portable OBS** (`C:\SOFTWARE\OBS-Studio`, copied from the desktop): new profile "4K 10 bit 422 QuickSync" (3840x2160 30, P216, Rec. 709 limited, Advanced output, Standard MOV, this encoder at High). 20 s from the AverMedia: 585 frames, 0 identical frames by hash, 0 repeats by the plugin, 44 Mbit/s, clean decode, natural colours. Two things that went wrong first, both outside the plugin: (1) a DirectShow source set to **P010 with Color Space "Default" gives strongly oversaturated, red skin**; set the source's Color Space to Rec. 709 and Range to Limited. (2) With a second USB capture adapter open at the same time, the AverMedia at 4K P010 (about 750 MB/s) got no bandwidth: Windows showed "not enough USB controller resources" and the recording was black (all frames identical). One active USB capture source at a time, or put the adapters on different controllers.
- `scripts/test-record.ps1` can now use a live DirectShow card: `-CaptureDevice <video_device_id from a scene file> -CaptureFormat 204` (204 = P010 in libdshowcapture's enum) `-Fps 30`.
- **Not tested**: the StudioEncoder settings window with the new entry, Resolve and Premiere playback of these files, longer recordings and start/stop cycles, 60 fps, other Intel GPUs (Arc A/B discrete, older Core Ultra, 11th-14th gen iGPUs; 4:2:2 10-bit HEVC encode support varies by generation), Linux (the code uses the oneVPL API and should build there with libvpl, not tried).
