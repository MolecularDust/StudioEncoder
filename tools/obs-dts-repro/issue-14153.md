### Expected Behavior

Stopping a Custom Output (FFmpeg) recording and starting the next one should give two independent, complete files, however quickly the second recording is started.

### Current Behavior

Now and then the new recording stops by itself about half a second after it starts. The log shows:

```
==== Recording Start ===============================================
process_packet: Error writing packet: Invalid argument
Output 'adv_ffmpeg_output': stopping
```

The file of the failed recording contains exactly one video frame, and its timestamp continues the previous recording: it is the frame that was being encoded when the previous recording was stopped. Five failed recordings out of 20 in the attached log, each listed with the recording before it (video stream, time base 1/30000):

| File | Video packets | First pts | Last pts |
|---|---|---|---|
| 17-41-08.mov (OK) | 56 | 0 | 55055 |
| 17-41-12.mov (failed) | 1 | 56040 | 56040 |
| 17-41-51.mov (OK) | 25 | 0 | 24024 |
| 17-41-54.mov (failed) | 1 | 25020 | 25020 |
| 17-42-29.mov (OK) | 86 | 0 | 85085 |
| 17-42-34.mov (failed) | 1 | 86070 | 86070 |
| 17-43-08.mov (OK) | 79 | 0 | 78078 |
| 17-43-13.mov (failed) | 1 | 79050 | 79050 |
| 17-43-50.mov (OK) | 35 | 0 | 34034 |
| 17-43-54.mov (failed) | 1 | 35010 | 35010 |

So the first packet written into the new file comes from the previous session, and the new session's first real packet (dts 0) is then rejected by `av_interleaved_write_frame` with EINVAL, consistent with FFmpeg's non-monotonic DTS check. In normal use this also shows up as FFmpeg's "non monotonically increasing dts" message.

### Steps to Reproduce

1. Settings > Video: 3840x2160, 29.97 fps. Settings > Advanced: Color Format P216, Rec. 709, Limited. These are the settings I tested with; a slow 4K encode makes the window larger.
2. Settings > Output > Advanced > Recording: Type "Custom Output (FFmpeg)", output to file, container mov, video encoder prores_ks with Video Encoder Settings `profile=3`, audio encoder pcm_s24le.
3. Add a Media Source that loops a 4K clip.
4. Start recording, stop after 2-4 seconds, start the next recording within about a second. Repeat.

About one in four restarts fails as described. For the attached log the start/stop was driven through obs-websocket (StartRecord / StopRecord) on a stock portable OBS 33.0.1 with only the bundled modules; the same happens when using the record button or hotkey.

### Anything else we should know?

Reading `plugins/obs-ffmpeg/obs-ffmpeg-output.c` (33.0.1; the functions involved are unchanged on master):

- `receive_video()` and `encode_audio()` run the encoder synchronously on OBS's raw video/audio callback threads and then `da_push_back()` the packet into `output->packets`. With a heavy encoder this takes a large part of each frame interval.
- `ffmpeg_output_stop()` -> `ffmpeg_output_full_stop()` calls `obs_output_end_data_capture()`, which only clears `data_active` and disconnects the raw callbacks later in `end_data_capture_thread()`. `default_raw_video_callback()` checks `data_active` without a lock, so a callback that has already passed that check keeps running.
- `ffmpeg_deactivate()` then runs immediately: it joins the write thread, frees everything in `output->packets` and calls `ffmpeg_data_free()`.
- A `receive_video()` that was mid-encode at that moment finishes afterwards and pushes its packet into the now-empty `output->packets`. That array belongs to the output object, not to the session, and nothing clears it on the next start (`ffmpeg_output_start()` / `try_connect()` only reset `ff_data`). The next session's write thread therefore writes this stale packet first, which matches the one-frame files above.

The same in-flight encode can also still be using the codec context while `ffmpeg_data_free()` closes it, which looks like a possible use-after-free (not observed as a crash here).

Possible fixes: discard any leftover packets when a new session starts, and make the stop path wait until no raw video/audio callback is still inside `receive_video()` / `receive_audio()` before tearing down `ff_data` (for example a mutex held by those callbacks and taken in `ffmpeg_deactivate()`, together with a flag they check under it).

I have not seen this with Standard recording (encoders owned by libobs plus ffmpeg-mux): quick start/stop cycles there have produced no errors in my tests.
